# Gift Radar

Telegram-бот для анализа коллекционных подарков. Покупка, продажа, кошельки и выставление лотов отсутствуют.

**Бот доступен только администраторам из `ADMIN_IDS`, исключительно в личном чате.** При пустом или некорректном списке доступ закрыт всем. Проверяется каждый входящий update: команды, inline-кнопки, текст и файлы. Группы и каналы не получают данные. Пользователи, которые были зарегистрированы раньше, но не входят в список администраторов, больше не получают уведомления.

Реализованы расчёты по завершённым продажам, сценарии, подробные расходы и ROI, фильтры, подписи, избранное, уведомления без повторов, SQLite и управление кнопками с переключателями ✅/❌. Portals, MRKT и Tonnel подключаются **одним ключом Thermos** прямо в боте: ключ проверяется автоматически, после чего сразу выполняется первая загрузка. **Автоматический сбор лотов через Thermos пока недоступен:** в доступной документации Thermos нет метода чтения рыночного каталога и истории продаж (см. «Что нужно для автосбора» ниже). История и лоты не выдумываются; до появления контракта источником данных остаётся разрешённый экспорт.

Подробности: [исследование источников](docs/SOURCES.md), [архитектура и формулы](docs/ARCHITECTURE.md), [формат разрешённого экспорта](docs/EXPORT.md).

## Обновление существующего хостинга с GitHub

Репозиторий приложения: https://github.com/nalpax/my-telegram-bot1, ветка `main`. Код магазина, платежей, заказов, обязательной подписки и админ-панели заменён аналитическим Gift Radar. История прежнего кода сохранена в Git.

Если хостинг запускает `python main.py` или `python -m bot.main`, менять команду не нужно: обе точки входа теперь запускают аналитику. Старые `BOT_TOKEN` и `.env` продолжают работать. `ADMIN_IDS` определяет администраторов, которым разрешён любой доступ к боту. `PAYMENT_PROVIDER_TOKEN`, `DATABASE_URL` и другие магазинные настройки новым кодом не используются. Не удаляйте старую БД, PostgreSQL volume или сохранённые файлы сервера: они не переносятся в аналитику и не затрагиваются обновлением исходников.

После обновления ветки `main` дождитесь сборки хостинга или вручную выполните Redeploy/Restart с повторной установкой `requirements.txt`. В Telegram отправьте **новую команду `/start`**: появится меню Gift Radar, прежняя клавиатура магазина будет убрана. Старые сообщения и кнопки в истории Telegram сами не исчезают; нажатие старой inline-кнопки предложит открыть новое меню.

Для Docker Compose выполните `docker compose up -d --build bot`. Новому боту PostgreSQL не нужен; старый контейнер БД может остаться как orphan, его данные не удаляются. Не используйте `down -v` для обновления. Новые файлы аналитики сохраняются в `./data` на сервере. Хостинг с автоматическим перезапуском должен подхватить заменённый Dockerfile; дополнительная CA требуется только при сборке через управляемый сетевой прокси, на обычном хостинге используется стандартное доверие TLS.

Наличие нового меню не означает готовность живого мониторинга: карточка каждой площадки раздельно показывает «ключ сохранён», «доступ подтверждён» и «данные получены».

## Linux: установка и проверка

Требуется Python 3.11 или новее (совместим с прежним Dockerfile хостинга). Команды выполняются из корня проекта:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pytest -q
.venv/bin/python -m gift_radar check
```

Проверка БД не обращается к рынкам и не требует токена. БД и миграции создаются автоматически в `data/radar.sqlite3`; исходные данные пусты. Повторная установка с тем же файлом зависимостей и повторное открытие БД поддерживаются.

## Windows PowerShell

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m gift_radar check
```

Активация виртуальной среды и изменение ExecutionPolicy не нужны. Код не использует Linux-only зависимости. Тесты в данной среде выполнены на Linux; отдельный запуск на Windows пока не проверен.

## Настройки и запуск Telegram

Получите токен своего бота у [BotFather](https://t.me/BotFather) и передайте `TELEGRAM_BOT_TOKEN` через секреты среды или защищённый механизм переменных окружения. Не помещайте токен в код, Git, логи, командную историю и не отправляйте его в чат. В облачной среде это требование сохранено в настройках, HTTPS-назначение `api.telegram.org`.

Приложение читает `.env` в рабочем каталоге; уже заданные переменные процесса имеют приоритет. Существующий `BOT_TOKEN` поддерживается как альтернативное имя `TELEGRAM_BOT_TOKEN`. Менять токен на хостинге не требуется. Путь `DATA_DIR` сохраняет совместимость с хостингом; новая БД — `radar.sqlite3`, старый `shop.db` не открывается. Дополнительные настройки:

| Переменная | По умолчанию | Значение |
|---|---|---|
| `GIFT_RADAR_DB` | `data/radar.sqlite3` | Путь SQLite |
| `GIFT_RADAR_SCAN_SECONDS` | `300` | Интервал фонового цикла, не меньше 30 секунд; персональный интервал уведомлений задаётся в боте |
| `GIFT_RADAR_RETENTION_DAYS` | `90` | Хранение рыночной истории, не меньше 30 дней |
| `GIFT_RADAR_LOG_DIR` | `logs` | Каталог журналов |

После настройки токена:

```bash
.venv/bin/python -m gift_radar bot
```

Перед запуском можно проверить токен и сеть без отправки сообщений: `.venv/bin/python -m gift_radar telegram-check`. Команда выполняет только `getMe` и не выводит токен или имя бота.

На Windows используйте `.venv\Scripts\python.exe -m gift_radar bot`. Нужен HTTPS-доступ к `api.telegram.org`; webhook, публичный порт и доступ к кошельку не требуются. В управляемой среде сохраняйте унаследованный HTTPS-прокси и CA; проверки TLS не отключать. Не запускайте несколько polling-процессов с одним токеном.

Откройте своего бота и отправьте `/start`. Главное меню состоит из четырёх разделов:

| Раздел | Что внутри |
|---|---|
| 🔎 Поиск | «Найти» (до 3 лучших кандидатов), «Обновить данные» (немедленный запрос площадок с отчётом), избранное |
| 🏪 Площадки | Доступ Thermos и карточки Portals, MRKT, Tonnel |
| 🔔 Уведомления | ✅/❌ автоуведомления, звук, «только новые лоты», ошибки подключения; интервал |
| ⚙️ Настройки | 📊 Анализ (переключатели), 🎯 Пороги и фильтры (числа и выбор), 🧾 Расходы, 💱 Валюты, 🛠 Дополнительно (статус, помощь, ID, удаление своих данных) |

Нажатие на переключатель меняет состояние, сразу сохраняется в SQLite и редактирует текущее сообщение, не создавая новых экранов. Повторное нажатие возвращает прежнее значение. Значки: ✅ включено, ❌ выключено, 🔒 недоступно до подключения, ⏳ идёт проверка, ⚠️ требует внимания. Во вложенных экранах есть «⬅️ Назад»; возврат отменяет незавершённый ввод, сохранённые настройки не меняются. Старые кнопки из истории чата не приводят к ошибке: бот предлагает открыть актуальное меню. Команды `/scan`, `/markets`, `/alerts`, `/settings`, `/cancel` и прежние `/help`, `/fees`, `/currency`, `/status`, `/favorites`, `/delete_me`, `/id` продолжают работать.

### Что делают переключатели

- **Площадка → Участвует в анализе**: выключенная площадка не участвует в поиске и уведомлениях и не получает новых фоновых запросов. Ключ при этом не удаляется. Повторное включение использует сохранённый ключ и при необходимости обновляет авторизацию.
- **Площадка → Поиск покупок / Поиск перепродажи**: площадка как место покупки и как место перепродажи в расчётах.
- **Уведомления → Автоуведомления**: без них фоновые карточки и сообщения об ошибках не отправляются. Включаются только вручную.
- **Звук**: при ❌ сообщения бота приходят с `disable_notification` (беззвучно).
- **Только новые лоты**: ✅ — одно уведомление на лот; ❌ — повторное уведомление, если цена этого лота снизилась после доставленного уведомления.
- **Ошибки подключения**: одно сообщение при поломке доступа Thermos или ошибке загрузки площадки и одно — при восстановлении.
- **Анализ → Подписанные подарки**: ❌ исключает подписанные подарки (это тот же параметр, что «Подпись» в фильтрах; там доступен и выбор «только подписанные»).
- **Анализ → Редкие варианты**: ❌ исключает подарки с редким свойством.
- **Анализ → Неполные данные в поиске**: ✅ показывает в «Поиске» кандидатов без полного расчёта с пометкой «⚠️ Неполные данные — не подтверждённая возможность». В уведомления такие кандидаты не попадают никогда.

Числовые пороги (прибыль, ROI, макс. цена, минимум аналогов, период, интервал) и списки фильтров редактируются вводом или выбором значений.

## Подключение площадок

Путь: **🏪 Площадки → площадка → 🔑 Подключить** (или «🔑 Подключить Thermos»).

1. Бот показывает короткую инструкцию и кнопку «🤖 Открыть @thermos». В [@thermos](https://t.me/thermos) отправьте `/api` — ключ выдаётся сразу, без поддержки.
2. Отправьте сам ключ одним сообщением в личном чате с ботом. Имена переменных вводить не нужно, переменные на хостинге не нужны.
3. Бот **сначала удаляет сообщение**; если удалить не удалось, ключ не сохраняется. Затем ключ шифруется и сохраняется.
4. Автоматическая проверка: `POST https://backend.thermos.gifts/api/v1/auth/api-token` с параметром `api_token` (документация Thermos). Успехом считается только HTTP 200 с токеном авторизации; JWT и сведения об аккаунте не сохраняются. Неверный ключ, 403, 429, ошибки сервера, сетевой сбой, таймаут и неожиданный формат различаются. Сетевой сбой не помечает ключ неверным; выполняется один повтор.
5. При подтверждённом доступе бот сам пишет «⏳ Загружаю первые данные…», запрашивает включённые площадки и присылает отчёт: что проверено, получены ли данные, сколько данных в базе, сколько подходящих предложений. Найденные предложения (до 3) приходят карточками и помечаются отправленными, чтобы фоновый цикл их не повторил. Если предложений нет, отчёт объясняет причины и что изменить. Если данные есть только по одной площадке, межплощадочная прибыль не рассчитывается.

Почему один ключ: Thermos — отдельный агрегатор swap.coffee. Его документация описывает операции с площадками `TONNEL`, `PORTALS` и `MRKT`, поэтому один ключ Thermos используется для всех трёх направлений, и интерфейс прямо это показывает. Это ключ Thermos, а не собственный ключ Portals, MRKT или Tonnel.

В «🔑 Доступ Thermos» есть «🔁 Проверить доступ», «🔑 Заменить ключ», «📖 Как получить ключ» и «🗑 Удалить доступ» (с подтверждением; настройки площадок и данные сохраняются). Ключ, сохранённый прежней версией в разделе Tonnel, используется как ключ Thermos без повторного ввода. В «⚙️ Дополнительно» карточки площадки: повторная проверка, загрузка разрешённого экспорта (JSON по [схеме](docs/EXPORT.md)), ссылка на площадку и удаление старого ключа Portals/MRKT, если он был сохранён раньше (бот его не использует: официальный способ проверки не подтверждён).

Фоновая работа: в существующем цикле (`GIFT_RADAR_SCAN_SECONDS`) бот обращается только к включённым площадкам. Авторизация Thermos обновляется не чаще срока жизни JWT (≈ раз в сутки), запросы сериализуются с интервалом не меньше 0,5 с (лимит Thermos — 2 запроса/с). После временной ошибки повтор не раньше чем через 10 минут, отклонённый ключ автоматически не перепроверяется. Ошибка одной площадки не останавливает остальные.

### Данные аккаунта Thermos (работает)

По Swagger Thermos (`https://backend.thermos.gifts/swagger-ui`) бот читает только два документированных метода, с JWT в заголовке `Authorization: Bearer`:

- `GET /api/v1/gifts/me/on-sale` — ваши лоты на продаже: «🔎 Поиск → 📦 Мои лоты Thermos»;
- `POST /api/v1/accounts/history` с `event_types=["GIFT_SELL"]` — ваши продажи. При включённых «🔔 Автоуведомлениях» бот сам присылает «💰 Продажа в Thermos» по каждой новой продаже, один раз; уже существующая история при первом запуске не рассылается.

Отчёт первой загрузки тоже показывает, получены ли данные аккаунта. JWT хранится только в памяти процесса, при истечении (HTTP 401) обновляется один раз сохранённым ключом. Торговых методов бот не вызывает. Суммы API приходят в нанотонах и показываются в TON.

### Что нужно для автосбора рынка

Проверка 17 октября 2026: в доступных источниках документации Thermos описаны авторизация, покупка/продажа/перевод подарков и список собственных лотов (`GET /api/v1/gifts/me/on-sale`), а подробности отсылаются к Swagger. Путь, параметры и формат ответа **метода чтения рыночного каталога** и **истории завершённых продаж**, а также способ передачи JWT в заголовке не найдены. Страницы `docs.swap.coffee` и `backend.thermos.gifts/openapi.json` из среды разработки недоступны (сетевой прокси). Эндпоинты не угадываются, поэтому адаптеры честно сообщают «🔒 автосбор недоступен».

Кнопка «🔑 Доступ Thermos → 📄 Описание API Thermos» скачивает с хостинга публичное описание API (Swagger UI `https://backend.thermos.gifts/swagger-ui`, без ключа и заголовков авторизации, только с хоста Thermos) и присылает его администратору файлом вместе со списком методов, похожих на каталог и историю продаж. Для включения нужен только этот публичный контракт без ключей: файл `https://backend.thermos.gifts/openapi.json` (или ссылка на раздел документации) с методами каталога лотов и истории продаж. После этого достаточно реализовать чтение в `ThermosMarketAdapter` (`gift_radar/adapters.py`); интерфейс, статусы, первая загрузка, фильтры и уведомления уже работают с ним.

Укажите свой настоящий Telegram ID в `ADMIN_IDS` на хостинге и перезапустите бота. При первом обращении закрытый бот сообщает только ваш собственный ID — без меню и данных. Допускается несколько положительных ID через запятую без пустых элементов. Непустой `GIFT_RADAR_ADMIN_IDS` переопределяет этот список. Пустая или некорректная конфигурация закрывает доступ всем. Права проверяются для каждой команды, кнопки, текста и файла, а также повторно после долгих сетевых операций и перед каждым фоновым сообщением.

Сам ключ принимается только на экране подключения Thermos в личном чате администратора. В остальных настройках известные секреты отклоняются, исходный ввод удаляется по возможности. Telegram-чаты с ботами не имеют сквозного шифрования; удаление сообщения не гарантирует удаления копий из инфраструктуры Telegram.

## Конфиденциальность

Ответы, карточки и уведомления отправляются с `protect_content=true`: Telegram запрещает штатную пересылку и сохранение такого содержимого. Это не гарантия против снимков экрана или внешнего копирования. Исходные текстовые сообщения с вводом и загруженные файлы бот пытается удалить после обработки; временные файлы импорта удаляются всегда. Старые сообщения и ранее сделанные копии этим обновлением не удаляются.

Ключи, введённые через отдельный экран, хранятся в SQLite только как шифротекст Fernet (аутентифицированное шифрование библиотеки `cryptography`). Зашифрованная запись привязана к площадке; подмена или повреждение не дают прочитать другой ключ. Токен бота остаётся в окружении/секретах хостинга. Прежние привязки переменных сохранены миграцией. При импорте исходный `raw` очищается от полей ключей, авторизации, сессий и лишних персональных сведений. Логи содержат категории ошибок; дополнительный фильтр маскирует известные секреты, включая сохранённые ключи после перезапуска, и удаляет тела исключений/stack trace.

При первом сохранении ключа автоматически создаётся приватный файл `<путь БД>.credentials.key`, обычно `data/radar.sqlite3.credentials.key`: настраивать переменную шифрования не нужно. **Каталог данных должен переживать Redeploy/Restart. Сохраняйте резервную копию БД вместе с этим файлом**, отдельно от Git. Docker Compose уже монтирует `./data`. При утрате/повреждении файла имеющиеся ключи не расшифруются: приложение блокирует доступ, требуется восстановление оригинального файла. Не удаляйте его для «исправления» ошибки. Ключ шифрования независим от токена Telegram-бота. Чтение ранее сохранённых привязок окружения оставлено для совместимости; интерфейс новых привязок больше не создаёт.

На Linux `.env`, база SQLite, её служебные файлы, файл шифрования и журналы получают права `0600` (чтение/запись владельцу); новые каталоги данных создаются с ограниченными правами. Если процесс не может защитить свой существующий файл, операция не продолжается. На Windows необходимы соответствующие NTFS ACL. Остальные данные SQLite не шифруются. Системный администратор и оператор хостинга сохраняют доступ к файлам, ключу шифрования и памяти процесса.

Ключ Thermos по предупреждению самого Thermos даёт полный доступ к аккаунту, включая перевод подарков и вывод TON. Gift Radar использует его только для запроса авторизации и не реализует торговых операций, переводов и запросов баланса. Не публикуйте ключ и не пересылайте его.

Порядок работы с данными:

1. Подключите Thermos в «🏪 Площадки» и посмотрите отчёт первой загрузки.
2. Пока автосбор недоступен, при наличии разрешённого реального экспорта загрузите его в «⚙️ Дополнительно» площадки. Затем «🔎 Поиск → Найти» покажет карточки.
3. Задайте расходы для каждой пары площадок и валюты: «⚙️ Настройки → 🧾 Расходы». Все расходы по умолчанию неизвестны; 0 — только для неприменимого сбора.
4. Настройте пороги и при необходимости курсы. При смене валюты порогов проверьте значения вручную.
5. Включите «🔔 Уведомления → Автоуведомления». Уведомление требует достаточных аналогов, уверенности не ниже средней, полного расчёта, свежих расходов и лота не старше 30 минут.

Кнопки карточки: открыть реальную ссылку (если есть), сравнить площадки, посмотреть аналоги/происхождение свойств, добавить в избранное, скрыть лот. В журнал не выводятся URL запросов или тексты сетевых ошибок с секретами. При неопределённой доставке уведомление не повторяется автоматически, поэтому возможен пропуск сообщения; это выбранная защита от дублей.

Реальный курс можно настроить оператором из своего законного источника: `python -m gift_radar rate TON USD <фактический_курс> --source <реальный_источник> --at <ISO_время_с_поясом>`. Значения в угловых скобках заменяются фактическими; в проекте нет демонстрационного курса. Пользовательский курс через `/currency` действует только для этого пользователя и помечается ручным. Курсы действуют один час.

## Постоянный сервер Linux

Запуск только на компьютере разработчика не обеспечивает непрерывную работу. Для сервера разместите проект, например в `/opt/my-telegram-bot1`, установите зависимости в его `.venv`, создайте отдельного пользователя `gift-radar` и предоставьте ему право писать в каталоги `data` и `logs`. Это действия администратора сервера, они не выполнялись в облачной среде.

В [deploy/gift-radar.service](deploy/gift-radar.service) приведён unit systemd. Проверьте пути и пользователя. Секреты передайте через защищённый `/etc/gift-radar.env` с правами чтения только нужных администраторов; unit читает его через `EnvironmentFile`. Скопируйте unit в каталог systemd и выполните:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now gift-radar
sudo systemctl status gift-radar
```

Проверьте ответ на `/status`, содержимое `logs/radar.log` и состояние источников в `/markets`. Для остановки — `sudo systemctl stop gift-radar`; при ручном запуске — Ctrl+C. Фоновая задача отменяется, соединения закрываются. systemd-конфигурация предоставлена для самостоятельного развёртывания, её работа на отдельном сервере здесь не проверена.

## Проверки и границы готовности

`python -m pytest -q` проверяет расчёты, подбор аналогов, подпись, комиссии, курсы, неизвестные расходы, фильтры, SQLite, дедупликацию, фоновые уведомления и Telegram-команды через искусственный транспорт. Весь искусственный материал находится только в тестах. `python -m gift_radar check` проверяет БД, количество записей, состояние источников и наличие токена без раскрытия его значения. Это не проверка токена через Telegram.

Тесты используют искусственные ключи и контролируемые HTTP-ответы; они не подтверждают работу настоящей авторизации. Живые запросы Telegram и Thermos из среды разработки не выполнялись. Для завершения подключения нужны: токен Telegram в секретах, применённые сетевые настройки и подтверждённые официальные источники с условиями использования, лимитами и схемой ответов. До этого нельзя считать непрерывный мониторинг рынков готовым. Опубликовать подготовленную облачную среду можно через настройки после просмотра и сохранения черновика; публикация и запуск в новой задаче пока не выполнены.
